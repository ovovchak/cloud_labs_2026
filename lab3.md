# Лабораторна робота 3

## Опрацювання даних з IoT-сенсорів за допомогою serverless-технологій

### Мета

Побудувати конвеєр обробки подій: емулятор датчиків надсилає вимірювання через REST у чергу повідомлень, serverless-функції обробляють повідомлення з черги і зберігають результати в базі даних, окремий REST-запит повертає історію вимірювань. У цій роботі не використовуються постійно запущені контейнери з попередніх лабораторних: усі обчислення виконуються функціями, які запускаються подіями і оплачуються за виклик.

### Передумови

- Акаунт у провайдера і бюджет із сповіщенням з лабораторної роботи 1.
- Робота виконується в окремому каталозі того самого репозиторію GitHub або в новому репозиторії — на вибір студента.

### Обмеження

- Діють обмеження лабораторної роботи 1: лише актуальні сервіси, усі хмарні ресурси описані в Terraform, секрети не зберігаються в репозиторії.
- Емулятор датчиків — єдиний компонент, який може працювати як звичайний процес (локально або в контейнері). Приймання, обробка і читання даних — лише через serverless-сервіси провайдера [^1].
- Емулятор запускається на 5–10 хвилин для демонстрації і зупиняється. Частота надсилання обмежена знизу 20 мілісекундами на один датчик, щоб не вийти за безкоштовні ліміти черги і функцій.

## Обов'язкові завдання (10 балів)

Завдання виконуються послідовно: кожне наступне використовує результат попереднього. Кожне оцінюється незалежно: студент, який виконав лише завдання 1, отримує 3 бали; завдання 1 і 2 — 5 балів, і так далі.

**1. Емулятор датчиків (3 б.)**
Програма, яка емулює роботу трьох датчиків різного типу — наприклад, температури, вологості та освітленості; кожен тип передає свій унікальний параметр вимірювання. Кожен датчик працює зі своєю частотою надсилання, яка задається в конфігурації (файл або змінні середовища) в діапазоні від 20 до 100 мілісекунд між надсиланнями. У конфігурації також задається адреса, на яку надсилаються дані, і ключ доступу до неї. Кожне повідомлення містить: ідентифікатор датчика, тип датчика, значення вимірювання з одиницею виміру, географічні координати датчика та час вимірювання. Емулятор пише в журнал кількість надісланих повідомлень і кількість помилок. Зберігається в каталозі `emulator/` із власним `Dockerfile` і інструкцією із запуску. Хмара для цього пункту не потрібна: емулятор можна розробити і перевірити на локальному приймачі.

**2. Приймання даних у чергу (2 б.)**
Емулятор надсилає кожне вимірювання окремим HTTP-запитом `POST` на публічну адресу приймача; тіло запиту — JSON із полями: `sensor_id` (рядок), `sensor_type` (одне з фіксованого переліку значень), `value` (число), `unit` (рядок), `location` (об'єкт з полями `lat` і `lon`), `measured_at` (час у форматі ISO 8601 в UTC). Приймач перевіряє ключ доступу в заголовку `x-api-key`, валідує обов'язкові поля і кладе повідомлення в чергу без обробки; відповідь — `202 Accepted` з ідентифікатором повідомлення або `400` з описом помилки валідації. Приймачем є HTTP-шлюз провайдера з прямою інтеграцією в чергу або мінімальна функція-приймач [^2]; черга — керований сервіс провайдера для обробки потоку подій [^3]. Усе в Terraform. У `docs/INGEST.md` — схема повідомлення, приклад запиту `curl`, пояснення, чому приймач не обробляє дані сам, а лише складає їх у чергу.

**3. Обробка даних функціями (3 б.)**
Дані з черги обробляються serverless-функціями, тригер яких — надходження нових повідомлень у чергу. Спроєктувати обробку для трьох типів датчиків і обґрунтувати дизайн: одна функція-диспетчер, яка розгалужує обробку за `sensor_type`, або окрема функція на кожен тип із маршрутизацією повідомлень на рівні черги чи теми. Обробка має містити принаймні одну змістовну дію для кожного типу — перевірку діапазону допустимих значень, перерахунок одиниць, обчислення відхилення від попереднього вимірювання або позначення аномалії. Функція має бути ідемпотентною: повторна доставка того самого повідомлення не створює дубля в базі. Функції — у каталозі `functions/`, розгортання — у Terraform [^4]. У `docs/PROCESSING.md` — схема потоку даних від емулятора до бази, обґрунтування вибраного дизайну, пояснення, як забезпечена ідемпотентність і що відбувається з повідомленням, яке функція не змогла обробити.

**4. Збереження і читання історії (2 б.)**
Спроєктувати таблицю або таблиці в реляційній базі даних провайдера [^5] для збереження вимірювань: обґрунтувати, чи це одна таблиця з полем типу або окрема таблиця на кожен тип датчика; передбачити індекс для запитів за датчиком і часовим діапазоном. Функції із завдання 3 записують оброблені вимірювання в базу. Окрема serverless-функція через той самий HTTP-шлюз обслуговує запит `GET /sensors/{sensor_id}/history` з параметрами `from`, `to` (час у форматі ISO 8601) і `limit`; відповідь — масив вимірювань у зворотному хронологічному порядку. У `docs/DATA.md` — схема таблиць з обґрунтуванням, приклад запиту історії і відповіді, пояснення, як функція підключається до бази і чому кількість одночасних з'єднань до бази є обмеженням для serverless-функцій.

## Бонусні завдання (до 5 балів)

**5. Черга недоставлених повідомлень (1 б.)**
Для основної черги налаштована черга недоставлених повідомлень (dead-letter queue): повідомлення, яке функція не змогла обробити після заданої кількості спроб (наприклад, трьох), переміщується в окрему чергу замість втрати або нескінченного повтору. Продемонструвати, надіславши повідомлення з навмисно некоректними даними, що воно опинилося в черзі недоставлених, а обробка решти не зупинилась. У `docs/DLQ.md` — налаштування, демонстрація і пояснення, хто і як має розбирати цю чергу.

**6. Нереляційна база для сирих даних (2 б.)**
Окрім реляційної бази, кожне вимірювання в первинному вигляді зберігається в нереляційній базі провайдера [^6] з ключем розділу `sensor_id` і ключем сортування `measured_at`. Запит історії із завдання 4 має варіант читання з нереляційної бази. У `docs/NOSQL.md` — порівняння двох підходів для цієї задачі: як виглядає запит історії в кожному, які запити зручні в одному і неможливі або дорогі в іншому, як масштабується запис при зростанні кількості датчиків, і висновок, який варіант обрати для потоку телеметрії і чому.

**7. Бінарні дані в об'єктному сховищі (2 б.)**
Четвертий тип датчика — камера, яка з періодом 10–30 секунд надсилає знімок (зображення розміром до 1 МБ). Зображення не передається через чергу і не зберігається в базі: емулятор отримує від функції одноразовий підписаний URL (presigned URL) для завантаження безпосередньо в об'єктне сховище провайдера [^7], завантажує файл, і лише після цього надсилає в чергу звичайне повідомлення з посиланням на об'єкт. У базі зберігається ключ об'єкта, а запит історії для камери повертає підписані URL для читання з обмеженим терміном дії. У `docs/BLOB.md` — послідовність дій з діаграмою, пояснення, чому бінарні дані не передають через чергу і не зберігають у базі, і що таке підписаний URL.

## Що здається

Посилання на репозиторій GitHub. У корені каталогу роботи — `README.md` з описом архітектури, публічною адресою приймача і структурою проєкту. Окрім коду, в репозиторії мають бути:

- `emulator/` — емулятор із `Dockerfile` та інструкцією із запуску.
- `functions/` — код serverless-функцій.
- `terraform/` — уся інфраструктура.
- `docs/ARCHITECTURE.md` — схема конвеєра від емулятора до запиту історії з призначенням кожного компонента.
- `docs/INGEST.md`, `docs/PROCESSING.md`, `docs/DATA.md` — за завданнями 2–4.
- Для бонусних завдань — `docs/DLQ.md`, `docs/NOSQL.md`, `docs/BLOB.md`.

## Важливо

- Захист проходить особисто. Слід бути готовим запустити емулятор, показати в журналах функцій обробку повідомлень у реальному часі, показати наповнення бази і виконати запит історії, а також відповісти на будь-яке питання з переліку нижче.
- Після захисту ресурси видаляються (`terraform destroy`). Черги і функції в межах безкоштовного рівня практично не коштують, база даних — коштує; забуті ресурси — відповідальність студента.
- Код емулятора, функцій і файли інфраструктури написані самостійно. Здача чужої роботи заборонена.

## Теоретичні питання до захисту

**Serverless**
1. Що таке serverless? Де в цій моделі сервери і хто ними керує?
2. Які переваги дає serverless порівняно з постійно запущеним контейнером? Які недоліки?
3. Що таке холодний старт функції? Від чого залежить його тривалість і як його зменшити?
4. Які обмеження мають serverless-функції: тривалість виконання, пам'ять, розмір пакета, кількість одночасних виконань? Що станеться при їхньому перевищенні?
5. Як функція масштабується під навантаженням? Чим це відрізняється від автоматичного масштабування контейнерів з лабораторної роботи 2?
6. Як формується вартість функції? Порахуйте вартість обробки одного мільйона повідомлень у вашій системі.

**Черги та події**

7. Навіщо між приймачем і обробником стоїть черга? Що станеться, якщо приймач писатиме в базу напряму?
8. Що таке гарантія доставки «щонайменше один раз» (at-least-once)? Чому черги надають саме її і що це вимагає від обробника?
9. Що таке ідемпотентність обробки? Як вона реалізована у вашій функції?
10. Що таке час видимості повідомлення (visibility timeout) і як він пов'язаний із тривалістю виконання функції?
11. Що таке черга недоставлених повідомлень і які проблеми вона розв'язує?
12. Чим черга відрізняється від теми (topic) з підписками? Коли потрібне одне, коли інше?
13. Чим спеціалізовані IoT-сервіси (AWS IoT Core, Azure IoT Hub) відрізняються від звичайної черги? Що таке MQTT і чому його використовують для датчиків замість HTTP?

**Мережа та доступ**

14. Що таке API Gateway? Які функції він виконує, крім маршрутизації запитів?
15. Як захищений ваш приймач від сторонніх запитів? Чим ключ API відрізняється від автентифікації через токен?
16. Що таке приватна і публічна мережа? Чи потрібна вашим функціям приватна мережа для доступу до бази і які наслідки її використання?

**Дані**

17. Які типи баз даних надають хмарні провайдери? Для яких задач призначений кожен тип?
18. Чому кількість одночасних з'єднань до реляційної бази є проблемою для serverless-функцій? Які є рішення?
19. Одна таблиця для всіх датчиків або окрема на кожен тип — які переваги і недоліки кожного варіанту?
20. Що таке ключ розділу (partition key) і ключ сортування в нереляційній базі? Чому для телеметрії обрано саме `sensor_id` і `measured_at`?
21. Чому бінарні дані не зберігають у базі і не передають через чергу? Що таке об'єктне сховище і підписаний URL?

## Довідка за провайдерами

[^1]: **Serverless-сервіси.** AWS — Lambda, API Gateway, SQS, DynamoDB, S3; Google Cloud — Cloud Functions або Cloud Run functions, API Gateway, Pub/Sub, Firestore, Cloud Storage; Azure — Azure Functions, API Management або HTTP-тригер функції, Service Bus або Event Hubs, Cosmos DB, Blob Storage.

[^2]: **HTTP-приймач.** AWS — `aws_apigatewayv2_api` (HTTP API) з інтеграцією типу `AWS_PROXY` напряму в SQS (`integration_subtype = "SQS-SendMessage"`), без функції; ключ API перевіряється авторизатором або порівнянням заголовка в шаблоні. Google Cloud — Cloud Function з HTTP-тригером, яка публікує в Pub/Sub. Azure — Azure Function з HTTP-тригером і вихідним прив'язуванням (output binding) до Service Bus.

[^3]: **Черги для потоку подій.** AWS — SQS (`aws_sqs_queue`; стандартна черга, безкоштовно 1 млн запитів на місяць) або, для спеціалізованого IoT-сценарію, IoT Core з правилами маршрутизації. Google Cloud — Pub/Sub (`google_pubsub_topic`, `google_pubsub_subscription`). Azure — Service Bus (`azurerm_servicebus_queue`) або Event Hubs для великих потоків; Azure IoT Hub — спеціалізований варіант.

[^4]: **Функції з тригером від черги.** AWS — `aws_lambda_function` та `aws_lambda_event_source_mapping` на чергу SQS; параметр `batch_size` визначає, скільки повідомлень отримує один виклик. Google Cloud — `google_cloudfunctions2_function` з `event_trigger` на тему Pub/Sub. Azure — функція з тригером Service Bus, розгортається через `azurerm_linux_function_app`. Для окремої функції на кожен тип датчика: в AWS — три черги і правило маршрутизації в API Gateway або SNS-тема з фільтрами підписок; в Pub/Sub — фільтри підписок за атрибутом; в Service Bus — тема з підписками і правилами.

[^5]: **Реляційна база для функцій.** Та сама база з лабораторної роботи 1 (RDS / Cloud SQL / Azure Database) або окрема. Для з'єднань із функцій: AWS — RDS Proxy (`aws_db_proxy`) або Aurora Serverless v2 з Data API; Google Cloud — Cloud SQL connector у коді функції; Azure — обмеження пулу з'єднань у коді. Функція має отримувати рядок підключення зі сховища секретів або змінної середовища, заданої в Terraform.

[^6]: **Нереляційні бази.** AWS — DynamoDB (`aws_dynamodb_table`, ключ розділу `sensor_id`, ключ сортування `measured_at`, режим оплати `PAY_PER_REQUEST`; безкоштовно 25 ГБ). Google Cloud — Firestore (`google_firestore_database`). Azure — Cosmos DB (`azurerm_cosmosdb_account`, `azurerm_cosmosdb_sql_container` з ключем розділу `/sensor_id`; безкоштовний рівень 1000 RU/s).

[^7]: **Об'єктне сховище та підписані URL.** AWS — S3 (`aws_s3_bucket`, доступ лише через IAM, `block_public_access`); підписаний URL створюється у функції через SDK (`getSignedUrl` для `PutObject` і `GetObject`) з терміном дії 5–15 хвилин. Google Cloud — Cloud Storage, signed URL через SDK. Azure — Blob Storage, SAS-токен (shared access signature) на окремий blob.
