# Лабораторна робота 1
 
## Розгортання застосунку на хмарному провайдері (AWS, Google Cloud або Microsoft Azure)
 
### Мета
 
Взяти власний застосунок з курсу «Бази даних і знань» (або будь-який власний REST API), запакувати його в контейнер, описати інфраструктуру як код, розгорнути в хмарі з керованою базою даних за балансувальником і налаштувати автоматичний деплой з GitHub. Вибір провайдера — на розсуд студента.
 
### Передумови
 
- Безкоштовний акаунт у одного з провайдерів: AWS Free Tier, Google Cloud Free Tier або Azure for Students. На root-акаунті увімкнена MFA; робота ведеться від окремого IAM-користувача, не від root.
- Перше, що робиться в акаунті, — бюджет із сповіщенням на email (AWS Budgets / GCP Budgets / Azure Cost Management).
- Уся робота — один репозиторій на GitHub: код застосунку, Dockerfile, Terraform, CI/CD workflow і документи здачі (див. «Що здається»). Здача без репозиторію не приймається.
### Обмеження
 
- Лише актуальні сервіси провайдера. Сервіси, позначені як deprecated або такі, що не приймають нових клієнтів, не приймаються (наприклад, AWS App Runner). Для запуску контейнера: AWS ECS Fargate або EC2, Google Cloud Run або Compute Engine, Azure Container Apps або Virtual Machines.
- Секрети (паролі до бази, ключі) не зберігаються у коді, образі чи репозиторії відкритим текстом — передаються через змінні середовища або `terraform.tfvars`, який у `.gitignore`.
- Доступ CI/CD до хмари — через OIDC і роль, а не через довговічні access keys у GitHub Secrets.
- Ручне створення ресурсів у консолі не зараховується. Все, що є в акаунті, має бути описане в Terraform.
## Обов'язкові завдання (10 балів)
 
Завдання 1 і 2 — послідовні: друге неможливе без першого. Завдання 3, 4 і 5 — незалежні одне від одного, кожне виконується поверх завдання 2 і оцінюється окремо. Студент, який зробив тільки 1 — отримує 2 бали; 1 і 2 — 5 балів; далі будь-яка комбінація з 3–5.
 
**1. Застосунок у контейнері (2 б.)**
REST API запакований у Docker-образ: Dockerfile у репозиторії, базовий образ із зафіксованою версією (не `latest`), залежності встановлюються окремим шаром до копіювання коду, процес працює не від root. `compose.yaml` піднімає застосунок разом із SQL-базою локально однією командою; дані бази — у volume і переживають `docker compose down`. Хмара для цього пункту не потрібна.
 
**2. Розгортання в хмарі через Terraform (3 б.)**
Уся інфраструктура описана в Terraform і створюється з порожнього акаунта командою `terraform apply`: приватний реєстр образів (ECR / Artifact Registry / ACR), керована SQL-база (RDS / Cloud SQL / Azure Database) і сервіс запуску контейнера (ECS Fargate або EC2 / Cloud Run або Compute Engine / Container Apps або VM). Рядок підключення до бази передається застосунку через змінні середовища і не комітиться в репозиторій. Застосунок доступний за публічною адресою і пише в керовану базу. `terraform destroy` прибирає все без залишку. Ресурси, створені в консолі руками, не зараховуються.
 
**3. Мережева ізоляція (2 б.)**
База даних розташована у приватній підмережі і не має публічної адреси; security group (firewall rule / NSG) бази дозволяє підключення лише від security group застосунку, не від IP-діапазонів. Застосунок не публікує портів, які не потрібні користувачу. Усі мережеві ресурси і правила — у Terraform.
 
**4. Load balancer (1 б.)**
Вхідний трафік приймає керований балансувальник провайдера (ALB / HTTP(S) Load Balancer / Application Gateway), а не контейнер напряму; балансувальник — єдине, що видно з інтернету. Health check налаштований на ендпоінт застосунку; У Terraform.
 
**5. Continuous deployment з GitHub (2 б.)**
GitHub Actions workflow: push у `main` → збірка образу → публікація в реєстр з тегом, що дорівнює хешу коміту → оновлення сервісу. Автентифікація в хмарі — через OIDC і роль, без збережених ключів доступу. При здачі внести зміну в код, запушити і показати, що вона з'явилась на публічній адресі без ручних дій.
 
## Бонусні завдання (до 5 балів)
 
**6. Безпека доступу (2 б.)**
Автентифікація користувачів API через керований сервіс провайдера (AWS Cognito, Firebase Auth / Identity Platform, Azure Entra ID) або JWT із перевіркою на стороні сервісу. Захищені ендпоінти повертають 401 без токена.
 
**7. Моніторинг (2 б.)**
Логи застосунку потрапляють у сервіс провайдера (CloudWatch / Cloud Logging / Azure Monitor). Налаштований дашборд з базовими метриками (кількість запитів, помилки 5xx, латентність, CPU/пам'ять) і хоча б один алерт з доставкою на email (наприклад, на помилки 5xx або непроходження health check). Усе — в Terraform.
 
**8. Документація API (1 б.)**
Список REST-ендпоінтів через OpenAPI/Swagger UI (springdoc-openapi, swagger-ui-express, drf-spectacular тощо), доступний за публічною адресою.
 
## Що здається
 
Посилання на репозиторій GitHub. У корені репозиторію — `README.md` з описом застосунку, публічною адресою і структурою проєкту. 

## Важливо
 
- Захист проходить особисто. Слід бути готовим змінити код і продемонструвати автоматичний деплой зміни, показати дані в базі і відповісти на будь-яке питання з переліку нижче.
- Після захисту ресурси видаляються (`terraform destroy`). Забуті ресурси — відповідальність студента.
- Код застосунку і файли інфраструктури написані самостійно. Здача чужої роботи заборонена.

## Теоретичні питання до захисту
 
**Хмара загалом**
1. Що таке регіон і зона доступності? Чому один сервер в одному регіоні не є надійним?
2. IaaS, PaaS, SaaS — де межа відповідальності між провайдером і вами в кожній моделі? До якої належить ваш сервіс?
3. Модель спільної відповідальності: за що провайдер не відповідає ніколи?
4. Вертикальне і горизонтальне масштабування. Чому горизонтальне вимагає stateless-застосунку? Чи ваш застосунок stateless?
5. Моделі оплати: pay-as-you-go, reserved, spot. Коли яка доречна? Що у вашій схемі коштує найбільше?
**Контейнери**
6. Чим контейнер відрізняється від віртуальної машини? Що між ними спільне на рівні ОС?
7. Образ, контейнер, реєстр. Чому образ незмінний?
8. Шари образу: чому порядок інструкцій у Dockerfile впливає на швидкість збірки? Показати на своєму Dockerfile.
9. Чому в тезі базового образу не використовують `latest`? Що означають `slim`, `alpine`, `bookworm`?
10. Чому дані не зберігають усередині контейнера? Де вони зберігаються у вашому проєкті?
11. Як контейнери в одній мережі знаходять один одного? Чому `localhost` усередині контейнера — не ваш `localhost`?
12. Навіщо Docker Compose, якщо є `docker run`? Що робить `depends_on` і чого він не гарантує?
 
**Мережа і безпека**

13. Публічна і приватна підмережа: що з вашої схеми має бути видиме з інтернету, а що — ні?
14. Security group / firewall rule: як працює, чому правило «від security group застосунку» краще за «від IP-адреси»?
15. Що таке балансувальник навантаження, що він робить із health check і що станеться, коли один екземпляр застосунку впаде?
16. IAM: користувач, роль, політика. Що таке принцип найменших привілеїв — і чи дотримано його у вашій роботі?
17. Чому сервіси отримують доступ через ролі, а не через ключі доступу?
18. Як ваш застосунок отримує пароль від бази? Де він зберігається і хто може його прочитати?
19. Що таке CDN? Призначення, переваги, недоліки. Чи потрібен він вашому застосунку?
 
**Дані**

20. Керована база проти бази у контейнері або на VM: що бере на себе провайдер? Що ви втрачаєте?
21. Що таке Multi-AZ і point-in-time recovery? Чи увімкнені вони у вас і чому?
 
**CI/CD та IaC**

22. Що таке CI і CD? Які етапи у вашому workflow і що робить кожен?
23. Чому тег образу — хеш коміту? Як відкотитись на попередню версію?
24. Як GitHub Actions отримує доступ до хмари без збережених ключів? Що таке OIDC і trust policy?
25. Що не так із створенням ресурсів у консолі? Які проблеми розв'язує Infrastructure as Code?
26. Що роблять `terraform init`, `plan`, `apply`, `destroy`? Що таке state і чому його не зберігають у git?
27. Як Terraform визначає порядок створення ресурсів? Показати залежність між ресурсами у своїх файлах.
28. Що станеться, якщо змінити ресурс у консолі руками, а потім запустити `terraform plan`?
